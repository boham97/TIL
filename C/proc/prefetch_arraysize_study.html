01동작 원리

서버가 응답 하나에 N행을 실어 보내고, 클라이언트가 버퍼에서 꺼내 쓴다.

PREFETCH=N이면 서버가 한 번의 페치 응답에 N행을 실어 보내고, OCI가 이를 내부 버퍼에 담아둔다. 이후 N−1번의 FETCH는 네트워크를 타지 않고 그 버퍼에서 행을 꺼낸다. 버퍼가 비면 다음 왕복으로 다시 N행을 채운다.

PREFETCH=1 (기본값)            PREFETCH=100
FETCH → [왕복] → 1행         FETCH → [왕복] → 100행을 버퍼에
FETCH → [왕복] → 1행         FETCH → 버퍼에서 꺼냄 (왕복 없음)
FETCH → [왕복] → 1행           ⋮  ×99
  ⋮                          FETCH → [왕복] → 다음 100행

10,000행 = 왕복 약 10,000회    10,000행 = 왕복 약 100회

The precompiler option PREFETCH allows for more efficient queries by pre-fetching a given number of rows. This decreases the number of server round trips needed and reduces overall memory usage.

When an OPEN is executed, the value of PREFETCH gives the number of rows to be pre-fetched when the query is executed.

Pro*C/C++ Programmer's Guide · 6-14

OPEN 시점에 첫 묶음을 이미 끌고 오므로 OPEN + 첫 FETCH가 한 왕복으로 합쳐진다.

사양
범위0 ~ 65535
기본값1 — 0이 아니다. 끄려면 PREFETCH=0을 명시해야 한다
적용 대상명시적 커서(DECLARE CURSOR + OPEN)만. SELECT INTO는 제외
자동 비활성화셀렉트 리스트에 LONG / LOB 포함 시

02배열 페치와의 관계

별개가 아니라 택일이다. 그리고 성능 차이는 생각보다 작다.

PREFETCH is used primarily to enhance the performance of single row fetches. PREFETCH has no effect when array fetches are used.

Pro*C/C++ Programmer's Guide · 6-14

배열 페치를 쓰는 커서에서는 PREFETCH가 무시된다. 둘을 같이 걸어 효과가 곱해지지 않는다. 즉 PREFETCH는 소스를 안 고치고 얻는 배열 페치다.

성능 차이의 근거

문서에는 “배열 페치가 더 빠르다”는 근거가 없다. 메커니즘상 차이는 두 가지이며 클라이언트 CPU에서만 발생한다. 서버 쪽 — 왕복 수, consistent gets, 전송 바이트 — 은 완전히 동일하다.

  1. 중간 복사 1회. 배열 페치는 OCIDefineByPos가 사용자 배열을 직접 가리키므로 네트워크 → 내 배열로 끝난다. PREFETCH는 네트워크 → OCI 내부 버퍼 → (FETCH마다) 스칼라 호스트 변수로 한 단계 더 거친다.
  2. EXEC SQL FETCH 실행 횟수. 10,000행이면 sqlcxt() 호출이 10,000번 대 100번. 매 호출마다 커서 상태 확인, SQLCA 갱신, WHENEVER 핸들러 평가가 붙는다.
호출당 오버헤드를 0.5~2 µs로 잡은 추정
결과 행 수배열 페치의 추가 절감 (클라이언트 CPU)판단
8,0004 ~ 16 ms노이즈
75,00040 ~ 150 ms미미
1,000,0000.5 ~ 2 초의미 있음

결론

수십만 행 이상이 아니면 둘의 성능 차이는 사실상 없다. 선택 기준은 성능이 아니라 위 표의 기능·코드 비용이다. 확인하려면 서버 통계로는 구분이 안 되므로 클라이언트 프로세스의 user CPU를 비교해야 한다 — getrusage(RUSAGE_SELF, &ru)의 ru_utime 델타.

03LONG / LOB 제약

여기서 LONG은 오라클 컬럼 타입이다. C의 long이 아니다.

CLOB/BLOB 이전에 쓰던 구형 대용량 타입. LONG은 가변길이 문자, LONG RAW는 가변길이 바이너리, 둘 다 최대 2GB다.

문서 16-2가 정리한 LOB 대비 제약
LOB은 랜덤 액세스 가능, LONG/LONG RAW는 순차 접근만← PREFETCH가 꺼지는 근본 이유
한 테이블에 LONG 컬럼은 하나만LOB은 여러 개
최대 2GBLOB은 4GB
“Oracle plans to end support of LONG and LONG RAW in future releases”CLOB/BLOB 이전 권장

헷갈리는 이름들

  • LONG VARCHAR / LONG VARRAW (4-7) — 컬럼 타입이 아니라 Pro*C 외부(호스트) 데이터타입. 4바이트 길이 필드 + 데이터 버퍼. EXEC SQL VAR ... IS LONG VARCHAR(n)으로 선언한다.
  • C의 long — 호스트 변수로 쓰면 오라클 NUMBER에 매핑되는 정수. 무관하다.
-- 남아 있는지 확인
SELECT owner, table_name, column_name, data_type
  FROM all_tab_columns
 WHERE data_type IN ('LONG', 'LONG RAW')
   AND owner = USER;

04적용 방법

옵션 한 줄이면 되지만, 위치와 스코프에 조건이 붙는다.

EXEC ORACLE OPTION (PREFETCH=200);

EXEC SQL DECLARE job_cur CURSOR FOR
    SELECT job_id, job_name FROM sched_job WHERE status = :st;

EXEC SQL OPEN job_cur;               /* 이 OPEN에 200이 실린다 */

EXEC ORACLE OPTION (PREFETCH=1);     /* 원복 */
네 가지 조건
조건내용
위치실행 순서가 아니라 소스 텍스트 순서로 적용된다. DECLARE가 아니라 OPEN 앞에 와야 하며, FETCH 앞은 이미 늦다.
스코프“stays in effect until textually superseded by another EXEC ORACLE statement” (10-10). 한 번 켜면 그 파일의 이후 모든 OPEN이 물려받으므로 원복이 필요하다.
커서 종류명시적 커서만. 단발성 SELECT INTO는 대상이 아니다.
데이터 타입배열 페치도 LONG/LOB도 아닐 것.

커맨드라인 — 파일 전체 일괄

shp_ora_proc.c: shp_ora_proc.pc
	$(ORA_SDK_HOME)/proc iname=shp_ora_proc.pc \
		parse=PARTIAL \
		prefetch=200 \
		...

현재 상태

Makefile에 prefetch=가 없으므로 전 커서가 기본값 1이다. 페치 1건당 왕복 1회. 다만 문서는 커서마다 적정치가 다르다며 인라인을 권장한다(6-14).

05측정 방법

SQL*Plus의 arraysize가 PREFETCH와 같은 OCI 손잡이를 돌린다.

set autotrace traceonly statistics   -- 통계만, 행 출력 생략
set timing on                        -- Elapsed 출력 (1/100초)
set arraysize 1                      -- 범위 1~5000, 기본 15
show arraysize
  • 첫 실행은 버린다. 파싱·딕셔너리 recursive gets가 섞인다. 각 arraysize마다 두 번 돌려 두 번째 값을 쓴다.
  • traceonly는 필수. 없으면 터미널 렌더링 시간이 섞여 효과가 묻힌다.
  • login.sql 또는 glogin.sql에 set arraysize 200을 넣으면 접속할 때마다 적용된다.
  • SET ARRAYSIZE는 SQL*Plus 자신의 페치에만 적용된다. PL/SQL 블록이나 SELECT INTO는 무관.
  • 여러 문장을 묶어 재려면 timing start … timing show … timing stop.

07왕복당 191바이트

쿼리도 뷰도 행 폭도 다른 세 측정에서 같은 상수가 나왔다.

TTC 응답 프레임 고정 비용

191.00 bytes / roundtrip 서버 → 클라이언트

반대 방향은 11.00 B/왕복 — “다음 거 줘” 수준의 압축된 TTC 호출이다. 데이터와 무관한 고정 비용이므로, 행이 좁을수록 상대적 손해가 커진다.

측정 27,119,334 ÷ 37,274191.00
측정 329,796 ÷ 156191.00
측정 4755,237 ÷ 3,954191.00

데이터 페이로드가 바이트 단위로 정확히 일치하는 것도 확인된다. 두 실행의 차이가 전부 왕복 오버헤드로 설명된다는 뜻이다.

          215,002 −   5 × 191 = 214,047

측정 2 10,189,072 − 37,350 × 191 = 3,055,222

191바이트의 정체

  • TNS 패킷 헤더(8 B), TTC 함수 응답 마커, 행 헤더(RXH)
  • 상태 블록(OER) — 에러 코드, 커서 ID, 누적 처리 행 수, 커서 상태 플래그. 여기가 제일 뚱뚱하다
  • 버전별 추가 세션 메타데이터

주의

이 값은 Oracle Net 계층 측정치다. TCP(20) + IP(20) + Ethernet(14) 헤더는 여기 포함되지 않으며, 실제 회선에서는 그 위에 추가로 붙는다.

행이 좁을수록 손해가 커진다

arraysize 1은 왕복당 2행이므로 행당 95.5 B가 붙는다. 전송 바이트 중 오버헤드가 차지하는 비율:

v$sesstat~20 B/행 · 예측82.7% 오버헤드

V$SESSTAT은 SID·STATISTIC#·VALUE·CON_ID가 전부 숫자라 행이 20 B 안팎이다. arraysize 1이면 전송량의 83%가 포장지가 된다 — 지금까지 중 bytes 절감이 가장 클 후보다. 다만 V$SESSTAT 풀스캔은 그 자체로 래치를 잡으므로, 왕복을 줄이면 래치 보유 시간도 함께 줄어든다는 점이 폴링 데몬에서는 더 중요하다.

08파이프라인 vs 블로킹

로지컬 리드가 줄어드는 조건은 실행계획의 모양이 결정한다.

규칙

arraysize / PREFETCH가 로지컬 리드를 줄이려면 페치 콜이 실제로 블록 pin을 유발해야 한다. 즉 실행계획이 파이프라인이어야 한다.

서버는 페치 콜 하나를 처리할 때마다 블록을 pin → 행 추출 → unpin 한다. 한 블록에 100건이 있는데 arraysize=1이면 그 블록을 100번 다시 pin해야 하고, 그게 전부 consistent gets로 잡힌다.

계획에 블로킹 오퍼레이션이 하나라도 있으면 소스 스캔이 첫 페치 콜(또는 execute)에 전부 끝나고 결과가 워크에어리어에 쌓인다. 이후 페치는 워크에어리어에서 퍼올 뿐이라 블록 pin이 없다.

파이프라인 — CG 줄어듦

  • 정렬·집계 없는 뷰
블로킹 — CG 안 줄어듦

측정 4 · 37,823 → 37,823

  • SORT ORDER BY
  • HASH GROUP BY / SORT AGGREGATE
  • HASH JOIN의 build 단계

X$ 고정 뷰(V$SQL, V$SESSTAT 등)는 공유 메모리 구조체라 애초에 버퍼 캐시 블록을 pin하지 않는다. 줄일 로지컬 리드가 0이다.

정렬을 넣으면 차이가 커지나?

방향이 반대다. ORDER BY는 arraysize 효과를 키우는 게 아니라 없앤다.

부작용으로 ORDER BY가 arraysize 1일 때의 CG를 줄여주긴 한다(56,591 → 17,500). 하지만 정렬 CPU와 temp I/O를 새로 지불하는 것이므로 최적화가 아니다 — 어차피 arraysize만 올리면 정렬 없이 같은 값을 얻는다.

초기 진술정정
“PREFETCH는 배열 페치와 별개로 왕복을 줄임”
— 원본 고도화 목록		 별개가 아니라 택일. 배열 페치 사용 시 PREFETCH는 무효다.
로컬 왕복 비용 25~50 µs 추정 실측 86 µs. “같은 장비면 이득이 크지 않다”는 과소평가였다 — 측정 4에서 3.8배.
“배열 페치가 여전히 더 빠르다” 문서 근거 없음. 클라이언트 CPU 차이뿐이며 수십만 행 이상에서만 유의미하다.
v$sql 67컬럼 행 폭 1.5 KB 추정 실측 669 B. 단, 클라이언트 페치 버퍼는 실제 길이가 아니라 선언 폭으로 잡히므로 메모리 산정은 선언 폭 기준을 유지한다.

10실전 권고

데몬에 무엇을, 얼마로, 어디에 걸 것인가.

값 선택

PREFETCH=100~200. 측정 2에서 100이 이미 최대 이득의 98%였고, 측정 4는 array 100에서 82왕복(이론 최소 81)으로 사실상 천장이었다. 1000까지 올릴 이유가 없다.

버퍼 메모리

PREFETCH × 선언된 컬럼 폭 합계. 네트워크로 오가는 실제 바이트가 아니라 선언 폭 기준이다.

  • v$sql 67컬럼 — 선언 폭 약 1.5 KB → PREFETCH 200이면 약 300 KB
  • OPTIMIZER_ENV, BIND_DATA(각 RAW(2000)) 포함 시 행 폭 5.5 KB → 200이면 1.1 MB. 모니터링 수집에는 불필요하므로 제외
  • SQL_TEXT VARCHAR2(1000)도 무겁다. SQL_ID 기준 별도 테이블에 신규만 적재하는 구조라면 본 수집 쿼리에서 제외

데몬 적용 시

  • 대량 커서에만 인라인으로 걸고 원복한다.
  • 같은 장비여도 접속이 루프백 TCP인지 확인 — select sys_context('userenv','network_protocol') from dual; 빈 값이면 bequeath, ipc면 IPC, tcp면 루프백 TCP로 왕복 비용이 3~5배다.
  • 같은 장비에서는 클라이언트와 서버가 같은 코어를 나눠 쓴다. 데몬이 태우는 TTC 파싱·버퍼 복사 CPU가 곧 DB가 못 쓰는 CPU다.
  • 효과 확인은 커서 전후로 v$mystat의 session logical reads 델타, 또는 10046 트레이스 후 tkprof의 query 컬럼.
