# TIL 2026-07-24 — 가변인자에 `0`을 넘기면 왜 깨지는가 (x86-64 어셈블리로 확인하기)

## 문제

`snprintf`로 고정폭 레코드를 만드는 코드에서, 아직 채우지 않은 필드에 `0`을 그냥 넣었다.

```c
snprintf(dst, 
        ...
         "%-20llu%-20llu%-20llu%-20llu"
         "%-20llu%-20llu%-10.6f",
         sid, serial, hash,
        ...
         0, 0, 0, 0, 0, 0, 0);   /* ← 여기 */
```

결과가 이상했다.

- `%llu` 6개 중 **앞 2개만** `140720308486144` 같은 거대한 값
- 뒤 4개는 정상적으로 `0`
- 마지막 `%f`에는 엉뚱한 소수점 값

## 원인 1 — 가변인자에는 기본 인자 승격이 `int`까지만 적용된다

가변인자(`...`)로 넘어가는 값에는 default argument promotion이 적용되지만,
`char`/`short` → `int`, `float` → `double`까지다.
**`int` → `long long`이나 `int` → `double`은 자동으로 안 된다.**

즉 포맷은 8바이트를 요구하는데 실제로는 4바이트짜리 `int`를 넘긴 상태다.

| 포맷 | 요구 타입 | 실제로 넘긴 것 |
|---|---|---|
| `%llu` | `unsigned long long` (8B, 정수 레지스터/스택) | `int` (4B) |
| `%f` | `double` (8B, **XMM 레지스터**) | `int` (4B) |

## 원인 2 — 어셈블리가 증거

`gcc -O0 -S`로 뽑아보니 이렇게 나왔다.

```asm
movl    $0, 96(%rsp)
movl    $0, 88(%rsp)
movl    $0, 80(%rsp)
movl    $0, 72(%rsp)
movl    $0, 64(%rsp)
movl    $0, 56(%rsp)
movl    $0, 48(%rsp)
...
call    snprintf@PLT
```

`movl` = **4바이트 저장**. 스택 인자 슬롯은 8바이트 정렬인데
하위 4바이트만 0으로 덮고 **상위 4바이트는 손도 안 댄다.**
`%llu`는 그 자리에서 8바이트를 통째로 읽으니 `0 + 이전에 남아있던 쓰레기`가 된다.

실제로 깨진 값을 16진수로 보면 정확히 맞아떨어졌다.

```
140720308486144 = 0x00007FFC_00000000
                    ^^^^^^^^  ^^^^^^^^
                    남아있던    내가 쓴 int 0
                    스택 주소 상위
```

`0x00007FFC…`는 리눅스 x86-64의 전형적인 **스택 주소 상위 절반**이다.

## 원인 3 — 왜 하필 앞 2개만 깨졌나

System V AMD64 calling convention의 인자 배치를 그려보면 답이 나온다.

```
rdi = dst
rsi = size
rdx = fmt
rcx = SID            ┐
r8  = SERIAL_NO      │ 정수 인자 6개까지는 레지스터 (항상 8바이트, 안전)
r9  = SQL_HASH       ┘
--- 7번째부터 스택 ---

[rsp+48] llu #1  ← int 0 (4바이트만 덮임) → 아래 남아있던 포인터 상위가 살아남음
[rsp+56] llu #2  ← 동일
[rsp+64] llu #3  ← 마침 그 자리가 0이어서 우연히 정상
...
```

`[rsp+48]`, `[rsp+56]`은 **직전에 실행된 함수가 포인터를 올려뒀던 자리**였다.
그보다 깊은 슬롯은 우연히 0이라 멀쩡해 보였을 뿐, 정상 동작이 아니었다.

> 교훈: "일부만 깨진다"는 건 버그가 없다는 뜻이 아니라 **운이 좋았다**는 뜻이다.

## 원인 4 — `%f`는 완전히 다른 경로

x86-64에서 부동소수점 인자는 정수와 **다른 레지스터(XMM0~7)**로 전달된다.
그리고 가변인자 함수 호출 시 `al` 레지스터에 **XMM 레지스터를 몇 개 썼는지**를 넣어줘야 한다.

```asm
movl    $0, %eax        ; al = 0 → "부동소수점 인자 없음"
call    snprintf@PLT
```

`0`은 `int`니까 컴파일러가 `al = 0`으로 설정한다.
그런데 포맷의 `%f`는 `va_arg(ap, double)`로 XMM 저장 영역을 읽으러 간다.
저장된 게 없으니 **거기 남아 있던 값**을 읽고, 그게 소수점 쓰레기값으로 찍힌다.

이게 단순히 값만 틀리는 문제가 아닌 이유:

- `snprintf`는 "잘리지 않았다면 필요했을 길이"를 반환한다
- `%f`는 지수 표기가 아니라 소수점을 전부 펼친다 → `1e300`이 남아 있었다면 **310자**
- `%-10.6f`의 `10`은 최소 폭일 뿐 **상한이 아니다**
- 고정폭 레코드라 뒤쪽 오프셋이 전부 밀려서 **수신 측 파싱이 통째로 깨진다**

## 해결

```c
0ULL, 0ULL, 0ULL, 0ULL, 0ULL, 0ULL, 0.0);
```

`ULL` 접미사는 C99부터 표준(6.4.4.1)이지만, gcc 기본 모드가 `gnu89`라 옛 컴파일러에서도 그냥 쓰인다.
(`-std=c89 -pedantic`을 붙이면 경고만 뜨고 동작에는 문제없다.)

이식성까지 챙기려면:

```c
#include <inttypes.h>
uint64_t v = 0;
snprintf(buf, sizeof buf, "%" PRIu64, v);
```

반환값 체크도 같이 넣어두는 게 좋다.

```c
n = snprintf(dst, size, FMT, ...);
if (n < 0 || n >= (int)size) {
    /* 절단됨 — 로그 남기고 레코드 폐기 */
}
```

## 확인 방법

고치기 전후로 어셈블리를 비교하면 확실하다.

```bash
gcc -O0 -S -masm=intel -o x.s x.c
grep -E "PTR \[rsp" x.s
```

- `mov DWORD PTR [rsp+48], 0` → **4바이트, 버그 확정**
- `mov QWORD PTR [rsp+48], 0` 또는 `push 0` → 정상

그리고 애초에 `-Wall -Wformat`을 켜면 대부분 컴파일 단계에서 잡힌다.
다만 포맷 문자열이 리터럴이 아니면(`snprintf(buf, n, fmt, v)`) 이 검사도 무력화된다.

## 한 줄 요약

**가변인자 함수는 타입 체크가 없다. 포맷이 8바이트를 요구하면 반드시 8바이트를 넘겨야 하고,
`0`은 `int`(4바이트)다. 의심스러우면 어셈블리를 보면 된다 — `movl`인지 `movq`인지가 전부 말해준다.**
