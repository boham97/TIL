calloc · brk · mmap — 실험 노트

임계값 래칫

"calloc으로 쓰고 다시 할당하면 RSS가 느는가"라는 질문 하나에서 출발해 glibc의 brk↔mmap 전환, mmap_threshold의 동적 상향("래칫"), tcache 재사용, calloc의 zero-fill 메커니즘까지 확인한 기록. 세션이 끊겨도 이어갈 수 있도록 남겨둠.

01

고정 크기 vs 가변 크기 반복 calloc

calloc(1, sz) → 4096바이트 memset → free를 50회 반복. 고정 모드는 sz가 항상 4MB, 가변 모드는 sz = 4MB + (i%17)×64KB로 매번 달라짐.

가변 모드에서 i=16 때 가장 큰 청크(~5.2MB)를 free하는 순간 glibc가 mmap_threshold를 그 크기로 즉시 올려버린다. 그 결과 i=17부터는 같은 크기의 요청이 새 threshold보다 작아져 brk로 빠지고, brk 힙은 자동 축소가 안 되니 RSS가 계단식으로 쌓인다.

동적 threshold (래칫 켜짐) — 계단식 증가 threshold 고정 — 끝까지 평평

README에 기록된 관측값(1,420 / 5,572 / 5,836 / 6,100 / 6,364 / 1,540 KB)을 바탕으로 재구성한 개형도. 초 단위 원시 로그가 아니라 실험 결론을 보여주기 위한 스케치임.

검증 — GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072로 threshold를 고정하면 동적 상향이 꺼져, 가변 모드에서도 50회 내내 mmap↔munmap만 반복하고 RSS가 끝까지 평평. strace로 brk/mmap/munmap 호출 순서를 직접 확인해 원인이 "동적 mmap_threshold 래칫"임을 확정함.
02

작은 크기(4KB) 반복 — 왜 매번 같은 주소인가

base=4KB로 줄여 반복하면 포인터가 계속 동일하게 나온다. memset으로 오염시켰는데 calloc이 매번 0을 보장한다면, 다른 주소를 새로 내주는 게 아닌가 하는 의문에서 출발한 확인.

  1. 4KB는 mmap_threshold(128KB)보다 훨씬 작아 애초에 brk 힙 경로만 탄다.
  2. free()는 이 크기에서 OS에 반납하지 않고 유저공간 free list(tcache 등)에만 넣어둔다 — 힙 페이지는 프로세스가 계속 보유.
  3. 동시에 살아있는 청크가 1개뿐이라 free→calloc이 LIFO로 정확히 같은 슬롯을 재사용 → 주소가 같다.
  4. calloc의 zero-fill 보장은 "커널이 갓 준 새 페이지는 원래 0"이라는 사실에 기댄 최적화일 뿐, 재활용된 청크를 내줄 땐 glibc가 내부적으로 명시적 memset(0)을 다시 수행한다. 직전에 memset(p,1,...)로 오염시켜도 다음 calloc의 첫 바이트는 항상 0이었음 (별도 zero_check.c로 확인).
  5. strace 상으로도 반복 구간 동안 brk/mmap/munmap이 전혀 발생하지 않아 순수 유저 공간 재사용임을 뒷받침.
03

128KB 경계 정밀 스윕 — 현재 main.c 상태

131072−64부터 131072+64까지 8바이트 간격으로 calloc → memset → free → malloc_trim(0)을 반복. trim이 없으면 free된 chunk가 top chunk에 합쳐져 다음 요청이 sysmalloc 판단 로직 자체를 안 타게 되어 threshold를 넘겨도 계속 brk로 착각한다 — 처음에 이걸로 한 번 낚였음.

glibc의 실제 chunk 크기 계산

nb = (req + 8 + 15) & ~15

기본(동적 threshold) 상태 strace_boundary.txt

size=131056에서 mmap 한 번 발생(페이지 정렬로 135,168바이트로 잡힘). 곧바로 free되며 "방금 munmap한 크기(135,168) > 현재 threshold(131,072)"라 threshold가 즉시 135,168로 상향된다. 다음 요청부터 다시 brk로 떨어지고, 테스트 범위 끝(nb=131,152)까지도 135,168을 못 넘어 mmap이 두 번 다시 나오지 않음 — 경계 근처에서도 같은 래칫이 작동함을 확인.

threshold 고정 상태 strace_boundary_fixed.txt

GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072로 래칫을 끄면 size=131056(nb=131,072)에서 정확히 brk→mmap 전환이 일어난 뒤, 나머지 전 구간(131,064~131,136)이 계속 mmap 유지. 포인터도 0x1fb48c0(brk)에서 0x7ff4e6551010(mmap)로 딱 한 번 바뀌고 끝까지 유지됨.

결론 — 128KB 경계는 "요청 바이트"가 아니라 16바이트 정렬로 계산된 chunk 크기(nb) 기준이며, 정확한 크로싱 지점은 요청 131,056바이트 (nb=131,072)였다. 이 경계를 넘는 mmap/munmap 한 번만으로도 페이지 라운딩 때문에 threshold가 즉시 재조정되므로, 반복적인 크로싱을 관찰하려면 threshold를 고정해야 한다.

brk vs mmap 개념 정리

brk 힙mmap
구조프로세스에 하나뿐인 연속 힙의 끝(program break)을 밀고 당김독립된 새 매핑 영역을 그때그때 생성
사용 조건 (기본)작은 요청 (< 128KB)큰 요청 (≥ 128KB)
free 시 OS 반납즉시 안 됨 — 중간 chunk는 free list 재활용, top만 축소 가능(malloc_trim)free() 즉시 munmap으로 완전 반납
속도빠름 — 유저공간 free list 재사용, 시스템콜 없음느림 — 매번 커널 페이지 테이블 조작
단편화생길 수 있음 → 계단식 RSS 증가의 원인안 생김 — 독립 영역 통째로 반납
주소 특징낮고 고정된 힙 영역높고 매번 다름 (0x7f...)

작고 자주 쓰는 메모리는 brk 힙에서 빠르게 재활용하고, 크고 어쩌다 쓰는 메모리는 mmap으로 받아 쓰자마자 반납하는 게 glibc의 설계 의도. 계단식 RSS 증가, 같은 주소 재사용, threshold 래칫 — 지금까지 본 현상은 모두 이 두 경로 사이의 전환 로직에서 나온 것이다.

파일 구성 & 재현

  • main.c128KB 경계 스윕 테스트 코드 (최신 상태)
  • a.out빌드 산출물
  • prog_boundary.txt / strace_boundary.txt기본(동적 threshold) 상태 결과
  • prog_boundary_fixed.txt / strace_boundary_fixed.txtthreshold 고정 상태 결과

재현 명령어

# 빌드
gcc -O0 -g -o a.out main.c

# 기본 실행 + strace
./a.out > prog_boundary.txt
strace -f -tt -e trace=brk,mmap,munmap -o strace_boundary.txt ./a.out > /dev/null

# threshold 고정 실행 + strace
GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072 ./a.out > prog_boundary_fixed.txt
GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072 \
  strace -f -tt -e trace=brk,mmap,munmap -o strace_boundary_fixed.txt ./a.out > /dev/null

각 실험은 main.c를 그때그때 다르게 고쳐가며 진행한 것이라, 재현하려면 해당 절의 코드로 바꿔 다시 컴파일해야 함.
