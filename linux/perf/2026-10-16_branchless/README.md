# 2026-10-16 branchless: branchy의 `if`를 산술식으로 바꾸면 분기 예측 실패가 사라지는가

## 목적
기준선에서 가장 무거운 함수는 branchy(58%)였다. 원인은 랜덤 데이터에서 `if (v[i] < 128)` 분기 예측이 50% 확률로 틀리는 것(8,400만 번)이었다.
소스를 **분기 없는 식**으로 바꿔서 이 비용이 사라지는지 확인한다.

```c
// 원본
if (v[i] < 128)
    s += v[i];
// 이번
s += (v[i] < 128) * v[i];   // 비교 결과(0 또는 1)를 곱함
```

- 기준선 폴더의 `demo_cmov.c`는 **컴파일러가** `if`를 cmov로 바꾸게 둔 버전이었다. 이번에는 **소스를 바꾸는** 방법이다.
- cmov와 벡터화를 막는 속성 `__attribute__((optimize("no-if-conversion","no-if-conversion2","no-tree-vectorize")))`은 그대로 두었다. 소스만 바꿔서 분기가 없어지는지 보기 위해서다.
- compute 등 다른 함수는 원본과 같다(compute-simd 변경은 포함하지 않음). 그래서 기준선과 직접 비교할 수 있다.

## 환경과 빌드
- 기준선과 같다: AMD Ryzen 5 7430U, perf 6.12, gcc 14.3.1 (기본 `-march=x86-64-v3`), `perf_event_paranoid=2`
- 빌드: `gcc -O1 -g -fno-omit-frame-pointer demo.c -o demo` (이 폴더에서)
- 바이너리(`demo`, `demo_base`)는 측정 후 지웠다. `perf.data`의 빌드 ID는 `ec2c232b…`이다.
- 출력은 원본과 같다: `42928701440.000000 42928701440.000000 5327791670 19.691044`

## 결과 1: 어셈블리 확인 (annotate_branchy.txt)

곱셈을 예상했지만 gcc는 **`cmovg`** 를 만들었다.
```
movl   (%rdx),%eax        ← v[i] 읽기
cmpl   $0x7f,%eax         ← v[i] > 127 ?
cmovgl %esi,%eax          ← 크면 0으로 바꿈 (esi = 0)   ← 분기가 아님
cltq                      ← int → long
addq   %rax,%rcx          ← s += (항상 실행)
addq   $0x4,%rdx
cmpq   %rdi,%rdx
jne                       ← 루프 분기만 남음 (거의 항상 맞힘)
```

### 알 수 있는 것
- `(cond) * x`는 "조건이면 x, 아니면 0"과 같다. gcc가 곱셈보다 싼 cmov로 바꿨다.
- 속성 `no-if-conversion`은 **`if` 분기를 cmov로 바꾸는 패스**만 막는다. 소스에 처음부터 분기가 없으면 막을 것이 없다.
- 루프 안의 데이터에 따른 분기(`jg`, `jmp`)가 사라지고 **루프 분기 `jne` 하나만** 남았다. 이 분기는 1,600만 번 중 마지막 한 번만 빼고 늘 같은 방향이라 예측이 거의 다 맞는다.

## 결과 2: `perf stat`

| 지표 | 원본 (stat_base) | **branchless (stat)** | 기준선 demo_cmov (참고) |
|---|---|---|---|
| 실행 시간 | 0.8655초 ±0.11% | **0.4421초** ±0.36% | 0.4418초 |
| cycles | 3.656G | **1.832G** | 1.84G |
| instructions | 3.604G | 3.693G | 3.69G |
| IPC | 0.99 | **2.02** | 2.00 |
| branches | 900.5M | **648.9M** | - |
| branch-misses | 84.18M (9.35%) | **1만 번 (0.00%)** | 9천 번 |

### 알 수 있는 것
- **전체 시간이 48.9% 줄었다(0.866초 → 0.442초).** 지금까지 한 개선 중 가장 크다. 컴파일러에 cmov를 맡긴 demo_cmov와 숫자까지 거의 같다. 결국 같은 기계어가 나왔기 때문이다.
- **명령어는 오히려 9천만 개 늘었는데 2배 빨라졌다.** IPC가 0.99에서 2.02로 올랐다. 명령어 수가 아니라 **CPU가 놀고 있던 시간**(예측 실패 후 파이프라인 재시작)이 문제였다는 뜻이다. compute-4acc에서 본 것(명령어 감소 ≠ 빨라짐)의 반대 경우다.
- **branches −251.7M 검산:** 원소당 분기 수는 원본이 `je`(루프), `jg`(조건), 그리고 절반의 확률로 `jmp`이므로 2.5개다. branchless는 `jne` 1개다. 1.678억 원소 × 1.5 = **2.517억**이고, 측정 차이 2.516억과 정확히 맞는다.
- **instructions +89.6M 검산:** 원소당 명령어는 원본이 항상 6개(addq, cmpq, je, movl, cmpl, jg)에 절반 확률로 3개(movslq, addq, jmp)라 평균 7.5개다. branchless는 8개다. 1.678억 × 0.5 = **8,390만**이고, 측정값 8,960만과 오차 범위(±0.15% ≈ 550만)를 조금 넘는 정도로 맞는다.
- **예측 실패 1번의 비용:** 줄어든 cycles 1.824G ÷ 줄어든 branch-misses 8,417만 = **약 21.7사이클**이다. 기준선 README의 "약 15~20사이클" 추정과 비슷하다. 명령어가 늘어난 비용까지 섞여 있으므로 순수한 예측 실패 비용은 이보다 조금 더 크다고 보면 된다.

## 결과 3: `perf report` (report.txt)

```
48.83%  compute    ← 기준선 24.57% (자기 시간은 그대로, 전체가 줄어서 비율이 2배)
18.39%  branchy    ← 기준선 58.46%
11.48%  sum_cols
11.27%  __random
```

- branchy 사이클: 기준선 3.67G × 58.46% ≈ **2.15G**에서 이번 1.832G × 18.39% = **0.337G**로 줄었다. **약 6.4배**다.
- 원소당으로는 2.15G ÷ 1.678억 = 12.8사이클에서 **2.0사이클**이 됐다.
- **이제 1위는 compute(49%)다.** compute-simd 변경(4배)을 함께 적용하면 다음으로 큰 효과를 볼 수 있다.

### 아직 모르는 것: 원소당 2.0사이클의 한계는 무엇인가
- 루프 한 바퀴는 8개 명령어이고 2사이클이 걸린다(branchy 안에서 IPC 약 4).
- 후보 1: **메모리 대역폭.** `v`는 1,600만 × 4B = **64MB**로 L3(16MB)보다 커서, 10번 반복할 때마다 DRAM에서 다시 읽는다. 640MB를 약 0.081초(0.337G ÷ 4.14GHz)에 읽으면 **약 8GB/s**다. 한 코어 스트리밍으로는 그럴듯한 값이다.
- 후보 2: 루프 자체의 처리량(분기 1개, 명령어 8개).
- 샘플은 load(`movl`)에서 2~4개 뒤인 `addq`에 몰려 있지만(skid), 이것만으로는 둘 중 무엇인지 구분할 수 없다.
- 확인 방법: M을 L2에 들어가는 크기(예: 64K개 = 256KB)로 줄이고 반복 횟수를 늘려서, 같은 원소 수일 때 원소당 사이클이 줄어드는지 본다.

## 결론
- **소스를 branchless로 바꾸면 분기 예측 실패가 완전히 사라지고, 프로그램 전체가 거의 2배 빨라진다.** 컴파일러가 cmov를 쓰도록 둔 결과와 같다.
- 명령어 수는 늘었지만 IPC가 2배가 됐다. 성능은 명령어 수가 아니라 **CPU가 놀지 않게 하는 것**으로 결정된다.
- 분기 예측 실패 1번의 비용은 이 CPU에서 약 20사이클 이상으로 확인됐다.

## 다음 할 일
1. **compute-simd와 branchless를 합친 버전**을 측정한다. 이론상 0.442초에서 compute 절감분(약 0.16초)을 빼면 약 0.28초가 나와야 한다.
2. branchy 원소당 2.0사이클이 메모리 대역폭 때문인지 확인한다(M을 줄인 실험).
3. 벡터화 금지 속성을 풀면(`-O3`) branchy도 SIMD화되는지 본다.
4. sum_cols 루프 순서 변경.
