# perf 결과 읽는 법 (입문)

`results/2026-10-15_demo-baseline/`의 실제 결과 파일을 예로 들어, perf 출력을 한 줄씩 읽는 법을 정리한 문서.
실험별 해석은 각 결과 폴더의 README.md에 있고, 여기는 "읽는 법" 자체를 다룬다.

## 0. perf로 하는 일은 딱 두 가지

| 방식 | 명령 | 비유 | 답해주는 질문 |
|---|---|---|---|
| **세기 (counting)** | `perf stat` | 자동차 계기판의 총 주행거리 | 프로그램 **전체**가 무엇을 얼마나 했나? |
| **찍기 (sampling)** | `perf record` → `report` / `annotate` | 1초마다 "지금 어디야?" 하고 묻기 | 시간을 **어디서** 썼나? |

CPU 안에는 **하드웨어 성능 카운터(PMU)**라는 계수기가 있다. 클럭이 한 번 돌 때, 명령어가 하나 끝날 때, 분기 예측이 틀릴 때마다 1씩 올라간다. perf는 이 계수기를 읽어 오는 도구다.

- `stat`은 끝난 뒤 계수기의 최종 값만 본다. 정확하지만 "어디서"는 알 수 없다.
- `record`는 계수기가 일정 값(약 100만 사이클)에 닿을 때마다 CPU를 잠깐 멈추고 "지금 실행 중인 명령어 주소"를 기록한다. 이것이 **샘플**이다. 많이 찍힌 곳일수록 시간을 많이 쓴 곳이다.

분석 순서는 항상 같다.
1. **stat**: 무엇이 문제인지 본다 (분기? 메모리? 아니면 그냥 일이 많음?)
2. **report**: 어느 함수가 문제인지 본다
3. **annotate**: 그 함수의 어느 명령어가 문제인지 본다

## 1. `perf stat` 읽는 법 (stat.txt)

```
3,674,928,416  cycles:u        ( +-  0.04% )  (83.27%)
3,596,741,048  instructions:u  #  0.98  insn per cycle
   84,062,704  branch-misses:u #  9.35% of all branches
0.86929 seconds time elapsed
```

**각 부분의 뜻**
- `:u`: user 공간만 셌다 (`perf_event_paranoid=2`라서 커널 쪽은 못 봄).
- `( +- 0.04% )`: `-r 3`으로 3번 돌렸을 때 실행마다 달라진 정도. 작을수록 믿을 만하다. 1%를 넘으면 실행할 때마다 결과가 출렁인다는 뜻이니 조심한다.
- `(83.27%)`: CPU 계수기 수가 모자라서 6개 이벤트를 번갈아 셌다(멀티플렉싱). 전체 시간 중 83%만 실제로 셌고 나머지는 비율로 추정했다.
- `#` 뒤: perf가 계산해 준 파생 값.

**cycles와 instructions가 가장 중요하다.**
- cycles 36.7억: CPU 클럭이 36.7억 번 돌았다. 약 4.2GHz × 0.87초 ≈ 36억이니 맞다.
- instructions 36.0억: 명령어를 36억 개 끝냈다.
- **IPC = 36.0 / 36.7 = 0.98**

**IPC가 왜 핵심인가?** 요즘 CPU는 한 클럭에 명령어를 4~6개까지 동시에 처리할 수 있다. IPC가 1이라는 것은 **능력의 1/4~1/6만 쓰고 나머지 시간은 놀았다**는 뜻이다. CPU가 노는 이유는 대부분 둘 중 하나다.
- **분기 예측 실패**: 길을 잘못 들어서 했던 일을 버리고 다시 시작함
- **메모리 대기**: 데이터가 캐시에 없어서 RAM에서 올 때까지(수백 사이클) 기다림

이 둘을 구분하려고 `branch-misses`와 `cache-misses`를 같이 센다.

### 분기 예측이 뭔데 비싼가?
CPU는 파이프라인(공장 컨베이어 벨트)으로 명령어 여러 개를 동시에 처리한다. `if`를 만나면 결과가 나오기 전에 **"아마 이쪽이겠지" 하고 미리 그쪽 명령어를 벨트에 올린다**. 맞으면 공짜고, 틀리면 벨트 위의 일을 다 버리고 처음부터 다시 해야 한다. Zen 3 기준으로 약 15~20 사이클을 잃는다.

`demo.c`의 `if (v[i] < 128)`은 v가 0~255 랜덤이라 **동전 던지기**다. 아무리 똑똑한 예측기라도 50%는 틀린다.

### 검산: 숫자가 맞아떨어지면 해석이 맞다

```
비교 횟수          = 2^24(1,677만) × 10회 = 1.68억 번
예상 미스          = 1.68억 × 50% = 8,390만
측정 미스          = 8,406만  ← 거의 일치 → 미스의 거의 전부가 이 if 하나 때문

손해 사이클        = 8,400만 × 약 20 = 약 17억
cmov 버전과의 차이 = 3.67G − 1.84G = 18.3억  ← 또 일치
```
결론: **"0.43초 차이는 전부 이 분기 하나 때문"**이라고 숫자로 확신할 수 있다. 이것이 perf 분석의 핵심 습관이다.

### cmov 비교가 결정적인 이유
`demo_cmov`은 **명령어 수가 거의 같은데(3.60G vs 3.69G)** 시간이 절반이다. "일을 덜 해서 빨라진 것"이 아니라 "**덜 기다려서**" 빨라진 것이다. cmov는 "조건이 참이면 값을 옮기고 아니면 그대로 둔다"는 명령어 하나라서, 갈림길 자체가 없으니 예측할 것도 없다.

## 2. `perf report` 읽는 법 (report.txt)

```
# Samples: 3K of event 'cycles:Pu'
58.46%  demo  demo       [.] branchy
 6.01%  demo  libc.so.6  [.] __random
 0.06%  demo  [unknown]  [k] 0xffffffffac842f24
```
- `Samples: 3K`: 샘플을 약 3,000번 찍었다. 36.6억 사이클 ÷ 3,000 ≈ **120만 사이클마다 한 번**.
- `58.46%`: 3,000개 샘플 중 58%가 branchy 안에서 찍혔다. 즉 **CPU 시간의 58%를 branchy가 썼다.**
- 열 순서: `Command`(프로세스 이름), `Shared Object`(어느 파일의 코드인지. `demo`면 내 코드, `libc.so.6`이면 표준 라이브러리), `Symbol`(함수 이름)
- `[.]`는 유저 코드, `[k]`는 커널 코드. 커널 쪽은 권한이 없어서 이름 없이 주소(`[unknown]`)로만 나온다. 0.06% 수준이라 무시해도 된다.
- `---branchy / __libc_start_call_main`: `-g`로 기록한 **콜스택**. "누가 이 함수를 불렀나"를 보여준다.

**주의할 점**
- **샘플링은 통계라서 오차가 있다.** 3,000개 샘플에서 0.38%는 약 11개다. sum_rows처럼 작은 값은 대략적인 크기만 믿는다.
- `__random` 6%는 main의 초기화(`rand()` 1,677만 번) 비용이다. 측정하고 싶은 대상이 아니어도 프로그램에 포함되어 있으면 같이 찍힌다.
- **우선순위 판단**: 58%짜리를 절반으로 줄이면 전체가 29% 빨라진다. 0.38%짜리를 0으로 만들어도 전체는 0.38%밖에 안 빨라진다. 그래서 위에서부터 고친다.

### sum_cols vs sum_rows: 15배 차이
같은 덧셈 400만 번인데 메모리를 읽는 **순서**만 다르다.

```
a[i][j] 메모리 배치 (행 우선):  a[0][0] a[0][1] a[0][2] ... a[0][2047] a[1][0] ...
                               └─────── 한 행 = 2048×8B = 16KB ──────┘

sum_rows: a[0][0]→a[0][1]→a[0][2]   8바이트씩 옆으로 이동
          캐시 라인(64B) 한 번 가져오면 double 8개를 연달아 씀 → 7번은 공짜
sum_cols: a[0][0]→a[1][0]→a[2][0]   16KB씩 점프
          매번 새 캐시 라인을 가져오고 8개 중 1개만 씀
          2048행을 돌고 다음 열로 오면 처음 라인은 이미 밀려남 (32MB > L3 16MB)
```

## 3. `perf annotate` 읽는 법 (annotate_branchy.txt)

```
 Percent │ 주소      명령어
   0.10  : 401200:  addq  $0x4, %rax       ← i++ (int라 4바이트)
  34.20  : 401204:  cmpq  %rsi, %rax       ← i < M ?
   4.55  : 401207:  je    0x401218         ← 끝났으면 탈출
   0.00  : 401209:  movl  (%rax), %edx     ← v[i] 메모리에서 읽기
  22.13  : 40120b:  cmpl  $0x7f, %edx      ← v[i] 와 127 비교
   3.75  : 40120e:  jg    0x401200         ← ★ v[i] > 127 이면 위로 점프 (= if 거짓)
   0.00  : 401210:  movslq %edx, %rdx
  31.69  : 401213:  addq  %rdx, %rcx       ← s += v[i]
   3.58  : 401216:  jmp   0x401200
```

어셈블리 읽는 법(AT&T 문법): `명령 원본, 대상` 순서. `addq %rdx,%rcx`는 `rcx += rdx`. `$0x7f`는 상수 127.

### 왜 범인인 `jg`는 3.75%밖에 안 될까? → skid

샘플을 찍으라는 인터럽트가 와도 CPU는 손에 든 일을 조금 처리한 다음에 멈춘다. 그래서 샘플은 **실제로 시간을 잡아먹은 명령어보다 조금 뒤**에 찍힌다.

이 예제에서는 `jg` 예측이 틀리면 CPU가 **올바른 쪽에서 다시 시작**하고, 그 재시작 지점에 샘플이 쌓인다.
- 실제로 점프한 경우(v ≥ 128) → `401200` 근처에서 재시작 → **`cmpq` 34%**
- 실제로 안 점프한 경우(v < 128) → `401210` 근처에서 재시작 → **`addq` 32%**

**두 갈래가 34% 대 32%로 거의 반반**이다. 데이터가 50:50 랜덤이라는 것과 정확히 맞는다. "샘플이 분기의 양쪽 착지점에 나뉘어 있다"가 분기 예측 실패의 전형적인 모양이다.

### sum_cols (annotate_sum_cols.txt)
`addq $0x4000,%rax`(16KB 점프)에 91%가 몰려 있다. 이 명령어 자체는 1사이클짜리 덧셈이다. 바로 위의 `vaddsd (%rax)`(메모리 읽기)가 캐시 미스로 기다린 시간이 skid로 한 칸 아래에 찍힌 것이다.

> **규칙: 싼 명령어(add, cmp)에 샘플이 몰려 있으면, 바로 위의 비싼 명령어(메모리 로드, 분기, 나눗셈)를 의심한다.**

### compute (annotate_compute.txt)
나눗셈 `vdivsd`가 범인이다.
```
compute가 쓴 사이클 = 3.67G × 24.57% = 9억
반복 1회당          = 9억 ÷ 2억 = 4.5 사이클
```
- **지연(latency)**: 나눗셈 하나가 시작부터 끝까지 걸리는 시간 ≈ 13.5사이클
- **처리량(throughput)**: 나눗셈기에 새 나눗셈을 넣을 수 있는 간격 ≈ 4.5사이클

반복마다 `1.0/i`는 서로 독립이라 앞의 나눗셈이 끝나기 전에 다음 나눗셈을 시작할 수 있다(세탁기에 빨래를 연달아 넣는 것처럼). 그래서 측정한 4.5사이클이 **처리량과 정확히 일치**한다. 이 함수는 "기다리는" 게 아니라 **나눗셈기가 쉬지 않고 최대 속도로 일하는 중**이다. 코드를 다듬어서 줄이기는 어렵고, 나눗셈을 SIMD로 4개씩 묶어 처리하는 식으로만 빨라질 수 있다.

## 4. 정리: 세 가지 병목이 perf에서 보이는 모양

| 병목 | stat에서 | report에서 | annotate에서 |
|---|---|---|---|
| 분기 예측 실패 (branchy) | IPC 낮음 + **branch-misses 높음** | 큰 비율 | 분기(jg) **양쪽 착지점**에 샘플이 나뉨 |
| 캐시 미스 (sum_cols) | IPC 낮음 + cache-misses 높음 | 같은 일을 하는 함수보다 훨씬 느림 | 메모리 로드 **바로 다음 줄**에 샘플이 몰림 |
| 연산 한계 (compute) | 별 특징 없음 | 큰 비율 | 비싼 연산(div) 바로 다음 줄. **사이클 계산이 처리량과 일치** |

### 아직 확실하지 않은 것
`cache-misses` 850만은 sum_cols만 해도 예상되는 2,100만보다 **적다**. 그래서 이 숫자를 "L3 미스 = RAM 접근"이라고 그대로 믿으면 안 된다. AMD에서 일반 이벤트 `cache-misses`가 실제로 무엇을 세는지 모호하기 때문이다. sum_cols만 따로 측정하거나 `perf list`로 AMD 전용 L2/L3 이벤트를 찾아 확인한다 (baseline README 결론 3번).
