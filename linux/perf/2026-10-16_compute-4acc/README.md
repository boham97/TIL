# 2026-10-16 compute-4acc: 누산기를 4개로 나누면 compute가 빨라지는가

## 목적
`compute()`의 `x += 1.0 / i`를 누산기 4개(a, b, c, d)로 나눠서 빨라지는지 확인한다.

```c
for (i = 1; i + 3 < L; i += 4) {
    a += 1.0/i; b += 1.0/(i+1); c += 1.0/(i+2); d += 1.0/(i+3);
}
for (; i < L; i++) a += 1.0/i;   // 나머지 처리 (원본과 같은 범위 1..L-1)
x = a + b + c + d;
```

- 이 기법은 **덧셈 의존 사슬**(`x`가 이전 반복의 `x`를 기다림)이 병목일 때 효과가 있다.
- 기준선 README는 "병목은 나눗셈기 처리량(약 4.5사이클/개)이고, 덧셈 사슬(약 3사이클)은 병목이 아니니 빨라지지 않을 것"이라고 예측했다. 이번 실험은 그 예측을 검증한다.
- 제안받은 코드에는 나머지 루프가 없었다. L=2억이면 마지막 3개 항(199999997~199999999)이 빠지므로 나머지 루프를 추가했다. 출력은 원본과 같다(`19.691044`).

## 환경과 빌드
- 기준선과 같다: AMD Ryzen 5 7430U, perf 6.12, gcc 14.3.1, `perf_event_paranoid=2`
- 빌드: `gcc -O1 -g -fno-omit-frame-pointer demo.c -o demo` (이 폴더에서 실행)
- 비교 대상: 같은 날 같은 조건에서 원본 `../../demo.c`를 `demo_base`로 빌드해서 다시 측정했다.
- 바이너리 두 개(`demo`, `demo_base`)는 측정 후 지웠다. `perf.data`의 빌드 ID는 `f1d0ffa7…`이다.

## 결과 1: `perf stat` (stat.txt와 stat_base.txt 비교)

| 지표 | 원본 (demo_base) | 4누산기 (demo) | 차이 |
|---|---|---|---|
| 실행 시간 | 0.8704초 ±0.03% | **0.8666초** ±0.04% | **-0.4%** (0.004초) |
| cycles | 3.673G | 3.657G | -0.016G |
| instructions | 3.604G | 3.296G | **-0.308G** |
| IPC | 0.98 | 0.90 | 낮아짐 |
| branches | 901.7M | 747.5M | **-154M** |
| branch-misses | 84.16M | 84.04M | 같음 |

### 알 수 있는 것
- **시간은 거의 그대로다(0.4%).** 명령어는 3억 개 줄었지만 사이클은 거의 줄지 않았다. 줄어든 명령어는 원래 병목이 아니었다는 뜻이다.
- **branches -154M 검산:** 원본은 원소마다 루프 분기(`jne`)가 1개라 2억 개다. 4개씩 묶으면 5천만 개다. 차이는 1.5억 개로, 측정값 1.54억과 맞는다.
- **instructions -308M 검산:** 루프 한 바퀴의 명령어 수(아래 annotate)는 원본이 원소당 6개(cvt, div, add, addq, cmpq, jne)이고, 4누산기가 4원소당 18개(cvt×4, div×4, add×4, leaq×3, addq, cmpq, jne)로 원소당 4.5개다. 2억 × (6 − 4.5) = **3.0억**으로 측정값과 맞는다.
  - (정정) 처음에는 18개를 15개로 잘못 세서 계산이 4.5억으로 안 맞았다. 그래서 "cmp+jne가 1개로 세어진다(매크로 퓨전)"고 추정했었다. 다시 세어 보니 퓨전 가정 없이 맞는다. `2026-10-16_compute-simd`에서도 퓨전 없이 세야 맞았다.
- IPC가 0.98에서 0.90으로 떨어진 것은 나빠졌다는 뜻이 아니다. 같은 사이클 동안 **쓸데없는 명령어(루프 관리)가 줄었을 뿐**이고, 나눗셈기를 기다리는 시간은 그대로다.

## 결과 3: `perf annotate` (annotate_compute.txt)

```
vcvtsi2sd %rax,%xmm2,%xmm0
vdivsd    %xmm0,%xmm1,%xmm0     1.07
vaddsd    %xmm0,%xmm3,%xmm3    20.95   ← a +=
leaq      0x1(%rax),%rdx        3.45
vcvtsi2sd %rdx,%xmm2,%xmm0
vdivsd    %xmm0,%xmm1,%xmm0     1.79
vaddsd    %xmm0,%xmm6,%xmm6    19.05   ← b +=
...                                    (c, d도 같은 모양, 각각 약 19~20%)
addq      $0x4,%rax             4.76
cmpq      $0xbebc1fd,%rax              ← 0xbebc1fd = 199999997 (나머지 시작점)
jne
```

### 알 수 있는 것
- gcc가 누산기 4개를 레지스터 xmm3/6/5/4에 따로 두었다. 의도대로 **덧셈 사슬은 4개로 나뉘었다.**
- 샘플은 여전히 `vdivsd` 바로 뒤의 `vaddsd`에 몰려 있다(skid). 4개 나눗셈에 거의 균등하게(약 20%씩) 나뉜다. **나눗셈 하나하나가 똑같이 비싸다**는 뜻이다.
- 나머지 루프(3회)는 gcc가 컴파일할 때 미리 계산해서 상수 3개를 더하는 코드로 바꿨다(`vaddsd 0xd8d(%rip)` × 3). 루프로 남지 않았다.
- **사이클 검산:** 3.657G × 24.58% = 0.899G 사이클을 나눗셈 2억 번에 썼다. **나눗셈 1개당 4.49사이클**이고 기준선의 4.5사이클과 같다. Zen 3 `divsd` 처리량(4.5사이클당 1개)과 정확히 맞는다.

## 결론
- **누산기를 4개로 나눠도 빨라지지 않는다.** 기준선 README의 예측대로다.
- 이유: 원본도 이미 나눗셈기 처리량(4.5사이클/개)에 묶여 있었다. 덧셈 사슬 지연(약 3사이클)은 그보다 짧아서 병목이 아니었다. 병목이 아닌 것을 풀어도 시간은 줄지 않는다.
- 누산기 분리는 **덧셈(또는 FMA) 지연이 병목인 루프**, 예를 들어 배열 합계 `s += a[i]`에서 효과가 있다. 그런 루프는 원소당 약 3사이클(지연)에서 0.5~1사이클(처리량)까지 줄일 수 있다.
