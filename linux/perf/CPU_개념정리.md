## 1. 파이프라인: 명령어를 겹쳐서 처리한다

### 빨래 비유
빨래는 세탁 30분, 건조 **40분**, 개기 20분의 3단계다. 빨래 4개를 한다고 하자.

- **파이프라인 없이**: 하나를 다 끝내고 다음 빨래를 시작한다. 4 × 90분 = 6시간이 걸린다(오후 6시 → 자정).
- **파이프라인**: 1번이 건조기에 들어가면 바로 2번을 세탁기에 넣는다. 30 + **40 × 4** + 20 = 210분이 걸린다(오후 6시 → 9시 30분).

여기서 두 가지를 알 수 있다.
- 빨래 **하나**가 끝나는 데 걸리는 시간(**지연, latency**)은 그대로 90분이다. 대신 **일정 간격마다 하나씩** 끝난다(**처리량, throughput**).
- 세탁이 끝나도 건조기가 비어 있지 않으면 기다려야 한다. **전체 속도는 가장 느린 단계(건조기)가 정한다.**

### CPU에서는
고전적인 RISC(MIPS R3000)의 5단계는 다음과 같다.
```
IF   명령어 가져오기 (Fetch)
ID   해석하기 (Decode), 레지스터 읽기
EX   실행 (덧셈, 주소 계산)
MEM  메모리 읽기/쓰기
WB   결과를 레지스터에 쓰기 (Write Back)
```
```
사이클:   1   2   3   4   5   6   7
명령1     IF  ID  EX  MEM WB
명령2         IF  ID  EX  MEM WB
명령3             IF  ID  EX  MEM WB
```
파이프라인이 꽉 차면 **매 사이클 명령어 하나가 끝난다**. CPI(cycles per instruction)가 1이고, 그 역수인 IPC도 1이다.

## 2. 파이프라인이 멈추는 세 가지 이유 (hazard)

파이프라인이 매 사이클 돌려면 두 가지가 필요하다. **다음에 할 일을 미리 알아야** 하고, **앞의 결과를 기다리지 않아야** 한다. 이것이 깨지면 파이프라인에 빈칸(**bubble**)이 생긴다.

| 종류 | 상황 | 빨래로 치면 | 오늘 실험 |
|---|---|---|---|
| **데이터 의존** (data hazard) | 다음 명령어가 앞 명령어의 결과를 써야 함 | 건조가 끝나야 갤 수 있음 | compute의 `x += ...` (매 반복이 앞의 x를 기다림) |
| **자원 부족** (structural hazard) | 같은 장치를 동시에 쓰려 함 | 건조기가 하나뿐 | compute의 **나눗셈기** (4.5사이클에 1개만 받음) |
| **분기** (control hazard) | `if` 결과가 나와야 다음 명령어를 알 수 있음 | 빨래가 깨끗한지 봐야 다음 단계를 정함 | branchy의 `if (v[i] < 128)` |

### 예: 데이터 의존
```
add $r3, $r2, $r1     ← r3 = r1 + r2
add $r5, $r4, $r3     ← r3이 필요한데 아직 레지스터에 안 쓰였음 → 대기
```
해결책은 **코드 재배치**(code reordering)다. 서로 상관없는 명령어를 둘 사이에 끼워 넣어서 기다리는 시간에 다른 일을 하게 한다. 보통 컴파일러가 해 준다.

- `compute-4acc`의 누산기 4개(a, b, c, d)가 이 방식이다. 의존 사슬 하나를 4개의 독립된 사슬로 나눴다.
- `compute-simd`에서는 `-ffast-math`를 주자 gcc가 같은 일을 **자동으로** 했다. ymm 레지스터 하나에 x를 4갈래로 나눠 더했다.

## 3. 분기 예측

분기 결과가 나올 때까지 파이프라인을 세워 두면 너무 느리다. 그래서 CPU는 **결과를 추측해서 미리 진행한다**.
- 맞으면 공짜다.
- 틀리면 추측해서 진행한 일을 전부 버리고, 올바른 명령어부터 파이프라인을 다시 채운다.

### 예측 방법
- **정적 예측**: "뒤로 가는 분기(루프의 끝)는 대부분 실행되고, 앞으로 가는 분기는 반반"이라는 경향을 이용한다.
- **동적 예측**: 분기마다 **최근에 실행됐는지/안 됐는지의 이력**을 기억해 두고 그 패턴으로 예측한다. 요즘 CPU는 모두 이 방식이고, 일반 코드에서는 95~99% 이상 맞힌다.

### 측정: 틀리면 얼마나 비싼가
`branchless` 실험에서 분기를 없앴을 때의 변화다.

| | 원본 | branchless |
|---|---|---|
| branch-misses | 8,418만 | 1만 |
| cycles | 3.656G | 1.832G |

줄어든 cycles 1.824G ÷ 줄어든 misses 8,417만 = **예측 실패 1번에 약 21.7사이클**이다. 명령어가 조금 늘어난 비용이 섞여 있으니 실제 비용은 이보다 약간 더 크다.

### branch-misses 9.35%를 읽는 법
원본 branchy 루프에는 분기가 3종류 있다.

| 분기 | 횟수 | 예측 |
|---|---|---|
| `je` (루프 끝났나?) | 1.68억 | 거의 100% 맞음 (늘 "아니오", 마지막에만 "예") |
| `jg` (**v[i] < 128?**) | 1.68억 | **약 50% 맞음**: 8,400만 번 틀림 |
| `jmp` (if 안에서 되돌아가기) | 0.84억 | 100% 맞음 (무조건 분기) |

- perf stat의 9.35%는 **프로그램 전체 분기 9억 개 중** 틀린 비율이다(8,400만 ÷ 9억).
- `jg` 하나만 보면 8,400만 ÷ 1.68억 = **50%**, 동전 던지기 수준이다.
- 비율이 낮아 보여도 **틀린 횟수 × 1번당 비용**(8,400만 × 21.7 ≈ 18억 사이클)으로 보면 프로그램 시간의 절반이다.

### 분기를 없애는 방법: cmov / branchless
- `s += (v[i] < 128) * v[i]`처럼 쓰면 분기가 아니라 계산이 된다. gcc는 이것을 `cmovg`(조건부 이동)로 만들었다.
- cmov는 **두 값을 다 준비해 두고 결과만 고르는** 방식이다. 추측할 필요가 없으니 틀릴 일도 없다. 1990년대 IBM RS/6000이 분기 양쪽을 다 해 보던 것과 같은 발상이다.
- 효과: 0.866초 → 0.442초, IPC 0.99 → 2.02. **명령어는 9천만 개 늘었는데 2배 빨라졌다.**
- 주의: 예측이 잘 맞는 분기(정렬된 데이터 등)라면 cmov가 오히려 느릴 수 있다. cmov는 두 값을 다 기다려야 하기 때문이다.

## 4. 요즘 CPU가 파이프라인을 키운 세 가지 방법

| 방법 | 뜻 | 빨래로 치면 | 실험에서 보이는 것 |
|---|---|---|---|
| **Superpipelining** | 단계를 더 잘게 나눔 | 세탁을 "물 받기/빨기/헹구기"로 쪼갬 | Zen 3는 약 19단계다. 단계가 많을수록 **예측 실패 때 버리는 양이 많아서** 21.7사이클이나 손해 본다. |
| **Superscalar** | 파이프라인을 여러 개 둠 | 세탁기, 건조기를 여러 대 둠 | **IPC가 1을 넘을 수 있는 이유**다. combined의 IPC 2.44는 한 사이클에 평균 2.44개를 끝냈다는 뜻이다. |
| **Out-of-order** (동적 파이프라인) | 멈춘 명령어를 두고 뒤의 명령어를 먼저 실행 | 건조기를 기다리는 동안 다른 빨래를 먼저 갬 | 아래 설명 |

### Out-of-order가 4acc 결과를 설명한다
compute 루프에서 나눗셈을 기다리는 4.5사이클 동안, CPU는 뒤에 있는 `addq`/`cmpq`/`jne`(루프 관리)를 **옆에서 미리 처리한다**.
- 그래서 4acc에서 루프 관리 명령어가 3억 개 줄었어도 시간은 그대로였다(−0.4%). 원래 공짜로 처리되던 명령어였기 때문이다.
- **"명령어 수가 줄었다 ≠ 빨라졌다"**: 병목이 아닌 것을 줄이면 시간은 줄지 않는다.

### Commit 단계와 perf
- 실행은 순서가 뒤섞여도, 결과를 확정(**commit/retire**)하는 것은 프로그램 순서대로 한다. 예측이 틀렸을 때 확정 전의 결과를 버릴 수 있게 하기 위해서다.
- perf의 `instructions`는 **확정된(retired) 명령어 수**다. 추측으로 실행했다가 버린 명령어는 세지 않는다.
- **skid**(annotate 샘플이 원인보다 1~2개 뒤에 찍힘)도 이 구조 때문에 생긴다. 샘플을 찍는 순간에는 여러 명령어가 파이프라인 안에서 함께 진행 중이다.

## 5. 지연(latency)과 처리량(throughput): compute 세 실험 비교

나눗셈기(`divsd`)의 지연은 약 13.5사이클이고, 처리량은 4.5사이클당 1개다. 그런데 compute의 반복마다 나눗셈은 서로 **독립**이다. 그래서 여러 나눗셈이 겹쳐서 실행되고, 한계를 정하는 것은 **처리량**이다.

| 실험 | 한 일 | 원소당 사이클 | 결과 |
|---|---|---|---|
| 기준선 | 스칼라 `vdivsd` | 4.5 | 나눗셈기 처리량이 한계 |
| compute-4acc | 덧셈 의존(지연 약 3사이클)을 4갈래로 나눔 | 4.49 | **효과 없음**: 덧셈 지연은 원래 병목이 아니었음 |
| compute-simd | `vdivpd ymm`로 한 번에 4개 나눔 | **1.12** | **4배**: 나눗셈 1번(4.49사이클)에 일을 4배 시킴 |

판단 기준은 이렇다.
- **의존 사슬의 지연**이 병목이면 누산기를 나눈다. 예: 배열 합계 `s += a[i]`
- **실행 유닛의 처리량**이 병목이면 한 번에 더 많이 처리하거나(SIMD) 그 연산 자체를 줄인다.
- 둘 중 무엇인지는 **반복당 사이클을 명령어 표(지연/처리량)와 비교해서** 판단한다.

## 6. 의사난수 `rand()`: 무작위인데 어떻게 결과가 매번 같나

`rand()`는 진짜 무작위가 아니라 **이전 상태로 다음 수를 정해진 공식으로 계산하는 의사난수**(pseudo-random)다. 시작점(시드)이 같으면 나오는 수열도 매번 똑같다. demo.c는 `srand(42)`로 시드를 고정했다.

시드 42로 직접 확인한 결과다(scratch 프로그램으로 실행, 파일로 남기지 않음).
```
처음 5개: 70 100 49 41 100          ← 몇 번을 실행해도 같음
v<128 개수: 8390092 / 16777216 (50.0088%)
branchy 결과 = 10 × 532779167 = 5327791670   ← demo 출력과 같음
```

이로부터 알 수 있는 것은 세 가지다.
- **모든 버전의 비교가 공정하다.** v 배열이 같으니 결과 차이는 코드에서만 나온다. 그래서 원본, branchless, combined의 출력이 모두 `5327791670`이었다.
- **많이 뽑으면 절반이 거의 정확히 절반이다.** 1,677만 개면 표준편차가 약 2,000개(0.012%)다. 그래서 "비교 횟수 × 50%" 같은 검산이 잘 맞는다.
- **그래도 예측기는 못 맞힌다.** 예측기가 보는 것은 분기 이력뿐이고 수열을 만드는 공식은 모른다. 의사난수는 이력에서 패턴이 보이지 않게 만들어져 있다. 반대로 v를 **정렬**하면 앞 절반은 계속 참, 뒤 절반은 계속 거짓이 되어서 분기를 그대로 둬도 거의 다 맞힌다.

## 7. RISC와 CISC

| | **RISC** (Reduced Instruction Set) | **CISC** (Complex Instruction Set) |
|---|---|---|
| 명령어 하나가 하는 일 | 단순함 (한 가지만) | 복잡함 (여러 가지를 한 번에) |
| 명령어 길이 | **고정** (보통 4바이트) | **가변** (x86은 1~15바이트) |
| 메모리 접근 | load/store 명령어만 가능 | 연산 명령어도 메모리를 직접 읽음 |
| 레지스터 | 많음 (32개 정도) | 적음 (x86-64 범용 16개) |
| 복잡한 일 | 컴파일러가 단순 명령어로 조립 | 하드웨어가 처리 |
| 대표 | ARM (스마트폰, Apple M), RISC-V, MIPS | **x86** (Intel, AMD) |

RISC가 파이프라인에 유리한 이유는 두 가지다. 길이가 같으면 다음 명령어의 시작 위치를 바로 안다. 명령어가 단순하면 단계마다 걸리는 시간이 비슷해서 가장 느린 단계에 덜 묶인다.

### 오늘 본 어셈블리가 CISC(x86)다
**연산 명령어가 메모리를 직접 읽는다** (sum_cols):
```
vaddsd (%rax),%xmm0,%xmm0     ← 메모리 읽기 + 덧셈을 명령어 하나로
```
RISC(ARM)라면 두 개로 나눠야 한다.
```
ldr   d1, [x0]                ← 메모리 읽기
fadd  d0, d0, d1              ← 덧셈
```

**명령어 길이가 제각각이다** (branchless의 branchy, 다음 주소와의 차이가 길이):
```
401220: mov   (%rdx),%eax     2바이트
401222: cmp   $0x7f,%eax      3바이트
401225: cmovg %esi,%eax       3바이트
401228: cltq                  2바이트
40122d: add   $0x4,%rdx       4바이트
```

### 지금은 경계가 흐려졌다
요즘 x86은 **겉은 CISC이고 속은 RISC**다.
- 해석(decode) 단계에서 x86 명령어를 단순한 내부 명령어 **μop**(micro-op)으로 쪼갠다. 예를 들어 `vaddsd (%rax),...`는 load μop과 add μop이 된다.
- 그 뒤의 out-of-order 파이프라인은 RISC 같은 μop으로 돌아간다.
- 가변 길이를 해석하는 비용이 크기 때문에, 한 번 해석한 μop을 저장해 두는 **μop 캐시**가 있다.

반대로 ARM도 SIMD, 암호화 명령어가 늘면서 "단순한 명령어만"이라는 원칙에서 멀어졌다. 그래서 지금 성능은 RISC냐 CISC냐보다 **파이프라인, 분기 예측, 캐시의 품질**로 결정된다. 오늘 실험에서도 시간을 결정한 것은 명령어 종류가 아니라 분기 예측 실패와 나눗셈기 처리량이었다.

## 8. 옛 글(1990년대)과 지금 다른 점

| 옛 글의 내용 | 지금 |
|---|---|
| 동적 예측은 90% 맞힌다 | 일반 코드에서 95~99% 이상 맞힌다. 다만 완전 랜덤 데이터는 어떤 예측기도 50%를 넘을 수 없다(branchy). |
| 단계가 많을수록 빠르다 | 너무 많으면 예측 실패 비용이 커진다. Pentium 4(약 31단계)가 대표적인 실패 사례다. |
| 데이터 의존이면 레지스터에 쓸 때까지 기다린다 | 결과를 레지스터에 쓰기 전에 다음 명령어로 바로 넘겨준다(forwarding/bypass). 정수 덧셈끼리의 의존은 약 1사이클만 기다린다. 오래 기다리는 것은 나눗셈 같은 긴 연산과 메모리 로드다. |
| 이상적인 CPI는 1 | superscalar라서 IPC 4~6까지 가능하다(Zen 3는 한 사이클에 6개까지 디스패치). |

## 9. 정리: perf 숫자 → 원인 → 해결

| perf에서 보이는 모양 | CPU 안에서 일어난 일 | 해결 | 실험 |
|---|---|---|---|
| IPC 낮음 + branch-misses 많음 | 분기 예측 실패로 파이프라인을 비움 | branchless, cmov, 데이터 정렬 | branchless: IPC 0.99 → 2.02 |
| IPC 낮음 + 특정 연산 뒤에 샘플 몰림 + 반복당 사이클 = 그 연산의 처리량 | 실행 유닛 처리량이 한계(자원 부족) | SIMD, 연산 횟수 줄이기 | compute-simd: 4배 |
| 반복당 사이클 = 의존 사슬의 지연 | 데이터 의존으로 대기 | 누산기 나누기 | (4acc는 이 경우가 아니어서 효과 없음) |
| IPC 낮음 + 메모리 로드 뒤에 샘플 몰림 | 캐시 미스로 메모리 대기 | 접근 순서 바꾸기, 데이터 줄이기 | sum_cols (아직 안 고침) |
| 명령어는 줄었는데 시간 그대로 | 줄인 명령어가 out-of-order로 이미 공짜였음 | 병목부터 찾는다 | compute-4acc |
