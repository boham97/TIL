# VM vs 컨테이너 성능 비교 논문 해석

> **원문**: Wes Felter, Alexandre Ferreira, Ram Rajamony, Juan Rubio (IBM Research, Austin),
> *An Updated Performance Comparison of Virtual Machines and Linux Containers*, IEEE ISPASS 2015, pp.171–172
> (원본은 2014년 IBM 연구 보고서 RC25482)
>
> - PDF: https://people.computing.clemson.edu/~jmarty/projects/lowLatencyNetworking/papers/NFVandContainers/AnupdatedPerfAnalysisofContainersandVMs.pdf

## 1. 한 줄 요약

**CPU와 메모리는 VM이든 컨테이너든 베어메탈과 거의 같다. 차이는 I/O와 OS와의 상호작용에서 난다.**
그리고 같은 조건에서 도커는 KVM과 같거나 더 빨랐다. 단, 도커도 기본 설정(NAT, AUFS)을 그대로 쓰면 성능 손해가 있다.

## 2. 무엇을 비교했나

|---|---|

| 서버 | IBM System x3650 M4, Xeon E5-2665 2소켓 (총 16코어 + 하이퍼스레딩), RAM 256GB, NUMA 구조 |

## 3. MySQL 실험 구성

SysBench OLTP로 MySQL 5.5에 부하를 주면서 **동시 접속 스레드 수를 늘려가며 초당 트랜잭션 수**를 측정했다.
비교한 구성은 5가지다.

| 구성 | 네트워크 | 데이터 저장 위치 | 의미 |
|---|---|---|---|
| **Native** | 호스트 | 호스트 파일시스템 | 기준선(베어메탈) |
| **Docker net=host volume** | 호스트 네트워크 그대로 | 볼륨(호스트 디렉터리) | 도커의 성능 손해 요소를 모두 제거한 상태 |
| **Docker NAT volume** | 도커 기본 브리지(NAT) | 볼륨 | 네트워크 비용만 추가 |
| **Docker NAT AUFS** | NAT | 컨테이너 내부 파일시스템(AUFS) | 도커 기본 설정 그대로 |
| **KVM qcow** | 가상 NIC | 가상 디스크 이미지(qcow) | 전통적인 VM |

> 메모리가 충분해서 DB가 거의 전부 메모리에 올라가 실제 디스크 I/O는 거의 없었다.
> 그래서 KVM의 스토리지 방식 차이는 결과에 영향이 없었다.

## 4. 그래프 해석

![MySQL throughput vs concurrency](fig1_mysql_throughput.png)

- **X축**: SysBench 스레드 수 (동시 사용자 수)
- **Y축**: 초당 처리 트랜잭션 수 (단위: 1000건)

### 4.1 구성별 최고 처리량 (그래프에서 읽은 근사값)

| 구성 | 최고 처리량 | Native 대비 |
|---|---|---|
| Native (빨강) | 약 13,300 tx/s | 기준 |
| Docker net=host volume (초록) | 약 13,000 tx/s | 약 -2% |
| Docker NAT volume (파랑) | 약 12,900 tx/s | 약 -3% |
| Docker NAT AUFS (보라) | 약 11,300 tx/s | 약 -15% |
| KVM qcow (하늘색) | 약 5,300~5,600 tx/s | 약 -60% |

> 논문 본문 기준으로는 도커와 Native의 차이가 동시성이 높아질수록 **약 2%에 수렴**하고,
> KVM은 **모든 측정 구간에서 40% 이상** 오버헤드가 있었다고 서술한다.
> 위 표의 퍼센트는 그래프를 눈으로 읽은 값이라 대략적인 수치로만 봐야 한다.

### 4.2 곡선 모양 읽기

1. **증가 구간 (0 ~ 약 150 스레드)**: 부하가 늘수록 처리량이 오르다가,
2. **포화 구간 (약 150 스레드 이후)**: 서버 자원이 다 차서 평평해지고,
3. **과부하 구간 (250 스레드 이후)**: 경합 때문에 아주 약간 떨어진다.

이건 어떤 시스템에서든 나오는 전형적인 모양이라 이상한 점은 없다. 중요한 건 **각 곡선의 높이 차이**다.

### 4.3 곡선 사이 간격이 의미하는 것

- **빨강 ↔ 초록 (거의 겹침)**: 컨테이너 자체의 비용은 거의 0이다.
  네임스페이스와 cgroup은 실행 경로에 끼어드는 층이 아니기 때문이다.
- **초록 ↔ 파랑 (살짝 벌어짐)**: NAT 비용. 이 워크로드는 네트워크를 많이 쓰지 않아서 차이가 작다.
  패킷을 많이 주고받는 워크로드라면 더 벌어진다.
- **파랑 ↔ 보라 (확 벌어짐)**: AUFS 비용. 컨테이너 내부 파일시스템은 여러 층을 거쳐 I/O가 일어나서 느리다.
  같은 NAT 조건에서 저장 위치만 바꿨는데 15% 가까이 차이 난다.
- **나머지 ↔ 하늘색 (크게 떨어짐)**: KVM 비용. 낮은 동시성(10 스레드)에서도 약 2,000 tx/s로
  다른 구성(약 3,300 tx/s)보다 뚜렷하게 낮고, 끝까지 따라잡지 못한다.

## 5. 논문의 주요 주장

### 5.1 CPU와 메모리
VM과 컨테이너 모두 CPU와 메모리에는 **오버헤드가 거의 없다**(극단적인 경우 제외).
영향은 I/O와 OS와의 상호작용에서만 생긴다.

### 5.2 I/O 오버헤드의 성격
I/O 한 번마다 **고정된 추가 비용**이 붙는 구조다. 그래서
- 큰 I/O는 비용이 묻혀서 거의 티가 안 나고,
- 작은 I/O를 자주 하면 비용이 쌓여 지연이 늘고 처리량이 떨어진다.

실제 서비스는 작은 I/O를 묶어서 처리하기 어려운 경우가 많아서 이 비용이 문제가 된다.

### 5.3 도커의 함정
도커의 편의 기능(레이어 이미지, NAT)은 성능 비용이 있다. **기본 설정 그대로면 KVM보다 나을 게 없을 수도 있다.**
- 파일시스템/디스크를 많이 쓰면 → **볼륨** 사용
- 네트워크 비용이 문제면 → **`--net=host`** 사용 (대신 네트워크 격리는 포기)

### 5.4 KVM의 약점
성능을 제대로 내려면 휴지페이지, CPU 모델, vCPU 고정, 캐시 구조 등을 세밀하게 설정해야 하는데,
문서화가 부실해서 시행착오가 필요했다. 튜닝해도 I/O마다 비용이 남아서
**지연에 민감하거나 I/O가 많은 워크로드에는 덜 적합**하다고 결론짓는다.

### 5.5 인프라 설계에 대한 제언
- VM 안에서 컨테이너를 돌리는 관행에 의문을 제기한다. VM 비용은 다 떠안으면서 얻는 이점이 없다는 것.
- 컨테이너는 VM 수준의 제어와 격리를 **베어메탈 수준의 성능**으로 제공할 수 있다.
- 컨테이너 자체는 처음부터 오버헤드가 거의 없었고 VM은 계속 빨라지는 중이라,
  장기적으로 컨테이너의 장점은 성능보다 **편의성, 빠른 배포, 탄력성**에서 나와야 한다고 본다.

## 6. 읽을 때 주의할 점 (한계)

| 한계 | 설명 |
|---|---|
| **오래된 환경** | 2014년 기준. 커널 3.11, Docker 1.0. 지금 도커는 AUFS 대신 **overlay2**를 기본으로 쓰고, KVM도 크게 개선됐다. 경향은 유효하지만 수치는 그대로 믿으면 안 된다. |
| **처리량만 봤다** | 그래프는 평균 처리량이다. **p99 같은 꼬리 지연**은 다루지 않는다. 평균이 같아도 꼬리는 다를 수 있다. |
| **디스크 I/O가 거의 없었다** | DB가 메모리에 다 올라간 상태라, 실제 디스크 I/O가 많은 환경의 차이는 이 그래프로 알 수 없다. |
| **cgroup 제한 없음** | 도커에 CPU/메모리 제한을 걸지 않았다. 실제 운영에서 `--cpus` 등을 걸면 throttling 때문에 결과가 달라질 수 있다. |
| **서버용 KVM 기준** | 노트북 위 버추얼박스 같은 데스크톱 하이퍼바이저는 이보다 훨씬 오버헤드가 크다. |

## 7. 직접 측정한 결과와의 연결

같은 주제로 간단한 C 도구(`lat`, `memwalk` 등)를 만들어 측정해본 결과도 논문의 결론과 맞았다.

- **베어메탈 vs 도커 (같은 서버)**: 제한 없이 돌리면 거의 같음 → 논문의 "컨테이너 오버헤드 거의 0"과 일치
- **베어메탈 vs 버추얼박스 VM**: 타이머 깨어남 지연(`lat sleep`)이 p50 약 56us → 약 0.8ms, p99는 수 ms~수십 ms로 급증
  → 논문의 "VM은 OS와의 상호작용(타이머, 인터럽트)에서 비용 발생"과 같은 방향. 다만 데스크톱 하이퍼바이저라 차이가 훨씬 컸다.
- **메모리 접근(`memwalk`)**: 휴지페이지 사용 시 개선 폭이 VM에서 더 컸음
  → 논문의 "KVM은 휴지페이지 설정이 성능에 중요"와 일치

측정 시 유의점:
1. 비교는 **같은 서버, 같은 시간대**에서 번갈아 실행
2. CPU 고정(`taskset`, `--cpuset-cpus`)과 전원 설정을 양쪽 동일하게
3. 꼬리 지연을 보려면 샘플을 수천~수만 개 이상

## 8. 결론

> **"도커는 베어메탈과 동급"은 맞는 말이지만 조건이 붙는다.**
> 제한 없이, `--net=host`로, 볼륨을 써서 돌리면 동급이다.
> 기본 설정(NAT + 컨테이너 내부 파일시스템)이나 CPU 제한을 쓰면 그만큼 손해가 생긴다.
> VM은 CPU 계산 자체는 빠르지만 I/O와 OS 상호작용마다 비용이 붙어서, 지연에 민감한 작업에서 불리하다.
